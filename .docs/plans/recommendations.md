## 3. Detailed reasoning (non-obvious verdicts)

**04-2 (onSettled vs onSuccess) — DISMISS from plan 04.** This is the one that changes a convention, so it was weighed carefully against the code. `useMutationWithInvalidation` wraps only `onSuccess` and is used at 119 sites; the ~7 optimistic sites in `Todos.tsx` each supply their own `onMutate`/`onError` that rolls the cache back to `ctx.previous` on failure. So after an optimistic error the cache is **already consistent with the last-known server truth** — the only thing `onSettled` buys is a re-fetch to _re-confirm_ that truth. Switching the wrapper to `onSettled` would flip failure-path behavior for **all 119 sites**, not just the optimistic ones: every mutation would now refetch on error, including non-optimistic mutations where a failed call changed nothing server-side. That is a broad behavior change with low upside for an app whose UI a single developer verifies by hand. Scoping `onSettled` to only the optimistic mutations would require a per-call flag and would fragment the convention (some sites `onSuccess`, some `onSettled`) — a net loss for the consistency this whole review optimizes for. Recommendation: **dismiss as a code change**; at most record a one-line "known limitation: invalidation is `onSuccess`-only; optimistic mutations rely on `onError` rollback for cache consistency" in the convention doc plan 04(d) already creates — so the choice is documented as deliberate, not silently blessed as "matches the docs verbatim." Do **not** open it as a follow-up refactor; the churn/benefit ratio doesn't justify a tracked task.

**03-1 (barrel tree-shaking) — KEEP-AMENDED.** The two invariants the reviewer wants asserted (barrels contain only re-exports; barrels stay cycle-free) are worth stating because plan 03's entire reason for existing is to break the settlement⇄expenses cycle, and a barrel re-exporting back through another barrel would silently reintroduce it — that's a readability/correctness note, essentially free. What to drop is the recommendation to add `madge --circular` to the committed verification. Introducing a dev-tooling dependency and a CI-ish check for a single-developer codebase is exactly "process ceremony without changing the outcome"; the plan's own section-5 grep audit plus `tsc -b` plus the new boundary lint rules already catch the regression. If the implementer wants a belt-and-suspenders pass, a one-off `npx madge --circular` run after step 9 is fine — as an ad-hoc check, not a repo dependency.

**01-1 (services off the isomorphic surface) — KEEP, with synergy note.** The note is cheap and correct, but the stronger point is that plan 03 makes it _enforced_, not just documented: the `isomorphic-shared-kernel` rule (regex `^(?!\./|temporal-polyfill$|zod$|superjson$).`) rejects any non-sibling import from `server/src/shared/**`, and a service would be reached via `../services/…`, which the `\./` branch does not match. So once plan 03 lands, an accidental `shared → services` edge is a lint error. Keep 01-1 as documentation, and cross-reference plan 03 so the two plans reinforce rather than restate each other.

**02-1 (Link href re-localization) — KEEP.** This is the residual runtime risk in the whole plan 02 bet. Output rewrites compute `href` at render time from `i18n.resolvedLanguage`; a `<Link>` in a component that doesn't call `useTranslation` won't re-render on `changeLanguage` and keeps a stale-locale href. The plan's `navigate({ to: ".", replace: true })` only fixes the address bar. Since the user verifies UI manually anyway, folding "after a locale switch, click an in-page link and confirm its href re-localized" into the existing smoke test is proportionate and catches a genuine defect class at zero tooling cost.

**06-3 (drop `is_head` alias) — KEEP as a conditional caveat.** Only relevant if the optional cleanup is taken, but the caveat is important because it reclassifies the change: removing `is_head` from `user.me` is an `AppRouter` output-shape change, so its safety proof is client `pnpm type-check`, not just server tests. Verified against plan 06's own analysis that no client code reads `me.is_head`, so it's safe — but the discipline of proving it via the client type-check should be explicit.

## 4. Cross-plan recommendations

**A. Lint-rule collision between plan 03 and plan 04(d) — NEW, must-fix.** Both add core `no-restricted-imports`. Plan 04(d) adds it to the unrestricted `"main"` block (all files); plan 03 adds per-feature blocks scoped to `client/src/features/${feature}/**` and a `components/**` block, inserted _after_ `"main"` (before `prettierConfig`). In flat config, rule options are **replaced, not merged**, by the last matching config object. Every raw-`useMutation` site plan 04(d) targets lives under `client/src/features/**` (`dashboard/…/useParking.ts`, `property/dangerzone`, `planstay/hooks`) — and all _future_ mutations will too. So if plan 03 lands after 04(d), plan 03's feature blocks silently strip the `useMutation` guard from exactly the files it's meant to police. Fix: the second plan to land must **merge both into one `no-restricted-imports` options object** in the generated feature blocks — the rule accepts `paths` (04(d)'s `useMutation`) and `patterns` (03's boundaries) together. Practically: land plan 03 first, then have plan 04(d) inject its `paths` entry into plan 03's per-feature block generator (and keep a `useMutation` `paths` rule in `"main"` for non-feature client dirs like `hooks/`, `routes/`). Note 03(c) uses the `@typescript-eslint/` variant on a different block, so it doesn't collide.

**B. Settlement mutation handlers are edited by three plans — sequence them.** Plan 05 Block A and plan 01 Step 0 both write settlement mutation-lifecycle characterization tests (05-4, both plans flag it) — write the shared `server/src/trpc/routers/settlement.test.ts` **once, first**. Then plan 01 extracts the mutation _bodies_ into services while plan 04(c) rewrites the authz _preamble_ of the same handlers (`advancePhase`/`regressPhase`/`acceptSplit`/`markTransferPaid`) — plan 01 explicitly keeps those head gates "in the router," which is exactly what 04(c) simplifies. They touch adjacent lines in the same handlers, so run them serially (01 then 04(c) on the slimmed router), never in parallel, with the characterization tests green throughout.

**C. wireMap (04a) after plan 01.** Plan 04(a) rewrites the `toWire*` helpers that plan 01 deliberately leaves in `settlement.ts`/`booking.ts`. Doing 01 first avoids reworking those two large files twice.

**D. Block B before any Todos decomposition (existing note, still valid).** No other plan decomposes `Todos.tsx`; plan 05 Block B's own tiny `parseTargetToken`/`TargetSelect` extraction is self-contained. Keep Block B's tests role/label-based so they survive it.

**E. Plans 02 and 06 are fully independent** (client routing; small server/i18n items) and can be done anytime without interacting with the settlement/lint sequencing above.
